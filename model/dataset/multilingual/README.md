# Multilingual PII Generation with Swappable Backends

This pipeline produces Label Studio tasks in ten languages. Two roles are
filled by pluggable backends:

| Role | What it does | Backends |
|------|--------------|----------|
| **Generator** | Writes a text of a given type in a given language and lists every span that could be personal data (candidates) | `workers-ai` (Qwen3.8-27B on Cloudflare), `openai-compatible` (local Qwen via vLLM / SGLang), `doubleword`, `fake` |
| **Decision model** | Decides, for every candidate, which PII label applies (or `NONE`) and returns a probability per label | `clef` (Cloudflare Clef-flash), `clef-local` (Clef served locally), `laya` (local `laya-serve`), `fake` |

Clef and Laya are *decision* models: they read a state and a set of typed
questions and return a probability for every allowed answer instead of
generating text. The pipeline therefore uses the LLM as a high-recall span
proposer and the decision model as the entity decider. The decision
probability becomes the per-entity `score` of the Label Studio prediction,
so reviewers can sort by confidence. The generator's intended label is kept
as `author_label` and the two are compared in `summary.json`.

```
┌────────────────────┐    ┌─────────────────────────┐    ┌──────────────────────┐
│ Plan sample        │───►│ Generator backend       │───►│ Decision backend     │
│ language × type ×  │    │ text + candidate spans  │    │ choice per candidate │
│ PII labels         │    │ (JSON schema output)    │    │ + noul "missing PII" │
└────────────────────┘    └─────────────────────────┘    └──────────┬───────────┘
                                                                    ▼
                                      ┌──────────────────────────────────────────┐
                                      │ samples/*.json  → labelstudio_tasks.json │
                                      │ labeling_config.xml, summary.json        │
                                      │ progress.json                            │
                                      └──────────────────────────────────────────┘
```

## Languages and text types

Ten languages are generated by default, each with locale-specific hints for
names, addresses, phone numbers and identifiers:

English, German, French, Spanish, Italian, Portuguese, Dutch, **Japanese**,
**Korean**, **Chinese (Simplified)**.

Samples rotate through twelve text types: business email, chat message,
support ticket, official form, news article, social media post, medical note,
legal excerpt, invoice, meeting minutes, job application, HR record. Both sets
live in [`config.py`](config.py); pass `--languages` / `--text_types` to use a
subset. The PII labels come from `LabelUtils.LABEL_DESCRIPTIONS` in
[`label_utils.py`](../label_utils.py), which also feeds the decision-model
options and the Label Studio config.

## Web UI

```bash
uv run python -m model.dataset.multilingual.ui            # http://127.0.0.1:8787
uv run python -m model.dataset.multilingual.ui --port 9000 --host 0.0.0.0
```

The page lets you pick the generator and decision backends (with their model
names and endpoints), the languages and text types, and the number of samples,
then starts the run in the background. Each run shows a progress bar, created /
skipped / failed counts, per-language counts, elapsed time and ETA, the latest
samples with their highlighted entities, errors, and a download link for
`labelstudio_tasks.json`. Runs can be cancelled; samples already written are
kept and exported. Choose the `fake` backends to try the flow without any
credentials.

The UI is a plain FastAPI app (`create_app()`); its JSON API is:

| Method | Path | Purpose |
|--------|------|---------|
| `GET` | `/api/options` | Languages, text types, labels, backends and defaults |
| `POST` | `/api/jobs` | Start a run (body mirrors `PipelineConfig`) |
| `GET` | `/api/jobs`, `/api/jobs/{id}` | Progress snapshots |
| `POST` | `/api/jobs/{id}/cancel` | Stop scheduling new samples |
| `GET` | `/api/jobs/{id}/samples?limit=5` | Latest samples as Label Studio tasks |
| `GET` | `/api/jobs/{id}/tasks` | Download `labelstudio_tasks.json` |

## Command line

```bash
# Cloudflare Workers AI for both roles (defaults)
export CLOUDFLARE_ACCOUNT_ID="..."
export CLOUDFLARE_API_TOKEN="..."   # token with the Workers AI "Read" permission
uv run python -m model.dataset.multilingual.pipeline --num_samples=100

# Local Qwen served by vLLM, Laya served by laya-serve
vllm serve Qwen/Qwen3.8-27B --port 8000 &
pip install "laya[serve]" && laya-serve --port 8001 &
uv run python -m model.dataset.multilingual.pipeline --num_samples=100 \
  --generator_backend=openai-compatible --generator_api_url=http://localhost:8000/v1/chat/completions \
  --decision_backend=laya --decision_api_url=http://localhost:8001/v1/systemone

# Clef-flash served locally from the open weights (see "Running Clef locally")
uv run model/dataset/multilingual/clef_server.py &
uv run python -m model.dataset.multilingual.pipeline --num_samples=100 \
  --decision_backend=clef-local

# Doubleword for generation, Clef for labeling, CJK only
export DOUBLEWORD_API_KEY="..."
uv run python -m model.dataset.multilingual.pipeline --num_samples=30 \
  --generator_backend=doubleword --generator_model=Qwen/Qwen3.8-27B \
  --languages="Japanese,Korean,Chinese (Simplified)" --text_types=support_ticket,chat_message

# Dry run without credentials
uv run python -m model.dataset.multilingual.pipeline --num_samples=10 \
  --generator_backend=fake --decision_backend=fake
```

Re-running the same command skips samples that already exist and rebuilds the
export from disk, so an interrupted or partially failed run is resumed by
running it again. Use `--overwrite` to regenerate.

## Backends in detail

**Generators** share one chat-completions payload (`backends/chat.py`): a
system prompt, the generation prompt and a strict JSON schema in
`response_format`. `<think>` blocks and code fences in the reply are stripped.

- `workers-ai` calls Cloudflare's OpenAI-compatible endpoint
  `/accounts/{id}/ai/v1/chat/completions`.
- `openai-compatible` posts to any URL you give it and adds
  `chat_template_kwargs: {"enable_thinking": false}`, which vLLM and SGLang
  honour for Qwen3-family models (Qwen3.8 otherwise reasons at length).
- `doubleword` is the same client pointed at `api.doubleword.ai/v1` with
  `service_tier: "priority"` for realtime responses and `DOUBLEWORD_API_KEY`.

**Decision models** receive a state and up to 64 questions per request:

```json
{
  "state": {
    "task": "Personal data (PII) annotation. The text was written in Japanese for Japan. ...",
    "text": "...",
    "candidates": [{"id": 1, "value": "田中"}, {"id": 2, "value": "太郎"}]
  },
  "questions": {
    "c1": {"type": "choice",
           "instructions": "Candidate 1 is the span \"田中\". Which kind of personal data is it in this text? Answer NONE if it is not personal data.",
           "criteria": {"FIRSTNAME": "A person's given name", "SURNAME": "...", "NONE": "Not personal data: ..."}},
    "c2": {"type": "choice", "...": "..."},
    "missing_pii": {"type": "noul",
                    "instructions": "Does the text contain personal data ... not covered by any candidate span?"}
  }
}
```

- `clef` posts this to Workers AI's `/ai/run/@cf/cloudflare/clef-flash`.
- `clef-local` posts the same state and questions (plus `model`) to
  [`clef_server.py`](clef_server.py)'s Jev-compatible `POST /v1/systemone`.
- `laya` posts to `laya-serve`'s Jev-compatible `POST /v1/systemone`, with the
  state rendered as plain text. Laya is a 512-token encoder, so the labeler
  switches to **one span per request with a text window** around the span
  whenever the text is longer than the backend's `max_state_chars` (1200 by
  default); the missing-PII question is skipped in that mode because it needs
  the whole text.

The answer parser (`backends/protocols.py` and `EntityLabeler.parse_choice`)
accepts the answers at the top level or under an `answers` key, reads
`probabilities` as a map or a list, and falls back to the arg-max when no
explicit `choice` is present. If a provider changes its field names, those two
places are the only ones to adapt.

### Running Clef locally

Clef's weights are open (Apache 2.0, `Cloudflare/clef-flash` and
`Cloudflare/clef` on Hugging Face). [`clef_server.py`](clef_server.py) loads
them and serves the same `POST /v1/systemone` API the hosted model speaks, so
labeling needs no Cloudflare account:

```bash
uv run model/dataset/multilingual/clef_server.py                 # Clef-flash on http://127.0.0.1:8002
uv run model/dataset/multilingual/clef_server.py --model Cloudflare/clef --device cuda --port 8002

uv run python -m model.dataset.multilingual.pipeline --num_samples=100 \
  --decision_backend=clef-local            # or pick "clef-local" in the web UI
```

The script declares its own dependencies (PEP 723), so `uv run` builds a
separate environment for it; Clef needs `transformers` 5.10+, which the rest of
the project does not allow. Things to know:

- The first start downloads the weights: about 19 GB for Clef-flash (9B),
  roughly three times that for Clef (27B). Cloudflare tested on a single H200.
  `--device` defaults to `auto` (CUDA, then Apple Silicon MPS, then CPU);
  Clef-flash in bfloat16 needs around 20 GB of GPU or unified memory. Use
  `--dtype` to override the precision.
- The server imports `joint_schema_model.py` from the model repository. Pass
  `--revision <commit>` to pin a copy you have reviewed, or `--model` with a
  local directory.
- It runs one request at a time, so `--max_workers` above 1 only parallelises
  generation. Set `CLEF_API_KEY` before starting the server to require a bearer
  token; the backend sends the same variable.
- Point the backend elsewhere with `--decision_api_url` or `CLEF_API_URL`, and
  set `--decision_model` to match what the server loaded so the samples record
  the right model name.

### Adding a backend

Implement the protocol in `backends/protocols.py` (a generator needs `model`
and `generate(prompt, json_schema)`; a decision model needs `model`,
`max_questions_per_request`, `max_state_chars` and `decide(state, questions)`)
and register it in `backends/__init__.py` with a `BackendSpec`. The CLI flags
and the UI pick it up from the registry.

### Which decision model?

Clef-flash (9B) and Clef (27B) are hosted and need no infrastructure, or run
locally with `clef-local` if you have the GPU memory; Laya
(0.3 to 0.4B) runs locally for free and covers over a hundred languages, but
has a short context and far less capacity for a 27-way label choice.
`summary.json` reports the agreement between the generator's intended label
and the decision model's verdict on every run, which is a cheap way to compare
the two on the same texts.

## Loading into Label Studio

1. Start Label Studio (`uv sync --extra labelstudio && uv run label-studio start`)
   and create a project, as described in the
   [Label Studio README](../labelstudio/README.md).
2. Paste `<output_dir>/labeling_config.xml` into the labeling interface editor.
   It is the standard config with `granularity="symbol"` so that Japanese,
   Korean and Chinese spans (which have no word delimiters) can be adjusted
   character by character.
3. Import `<output_dir>/labelstudio_tasks.json` (or download it from the UI).
   Entities appear as pre-annotations with their probability; `meta` shows
   which candidates were rejected and how likely it is that the text contains
   unlisted PII.
4. Review, export the annotations, and feed them to the training pipeline like
   any other Label Studio export.

Offsets are Python character (code point) indices, consistent with the other
generators and `tokenization.py`. Characters outside the Basic Multilingual
Plane (most emoji) count as two units in Label Studio's UI, so a prediction
after an emoji may be shifted by one; the prompt asks for plain text to keep
this rare.

## Programmatic use

```python
from model.dataset.multilingual import (
    EntityLabeler,
    PipelineConfig,
    ProgressTracker,
    build_decision_model,
    build_generator,
)
from model.dataset.multilingual.pipeline import GenerationPipeline

config = PipelineConfig(
    num_samples=20,
    languages=["Japanese", "Korean"],
    generator_backend="doubleword",
    decision_backend="laya",
)
pipeline = GenerationPipeline(
    config,
    build_generator(config.generator_backend),
    EntityLabeler(build_decision_model(config.decision_backend)),
)
tracker = ProgressTracker(on_update=lambda snapshot: print(snapshot["percent"]))
tasks = pipeline.run(tracker)
```

Any object with a `generate(prompt, json_schema)` method can act as the
generator, and any object with `decide(state, questions)` as the decision
model (see `backends/fake.py` and `tests/test_multilingual_pipeline.py`).
